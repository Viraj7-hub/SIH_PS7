## Nautilus Route Intelligence Engine
**SIH 2026 | Backend Member 2**

---

## 1. Graph Model

### Nodes
| Type | Count | Source |
|---|---|---|
| Ports | 55 | MySQL `ports` table (loaded at runtime) |
| Maritime waypoints | 30 | Static JS constants in `graph.builder.js` |
| **Total** | **~85** | |

Waypoints are corridor anchors covering: Gulf of Aden, Arabian Sea, Laccadive Sea, Bay of Bengal, Malacca Strait, Mozambique Channel, South Indian Ocean, and more.

### Edges
Auto-generated by connecting any two nodes within `MAX_HOP_NM = 1800` nautical miles using the Haversine great-circle formula.

**Edge object:**
```js
{
  from:          string,   // node id
  to:            string,   // node id
  distanceNM:    number,   // great-circle distance
  travelTimeHrs: number,   // distanceNM / vessel.maxSpeed
  fuelCost:      number,   // distanceNM × fuelConsumptionRate (tons/NM)
  safetyRisk:    number,   // base risk [0..100]; weather injection adds more
  maxDraft:      number,   // max vessel draft allowed (metres)
}
```

**Edge count estimate:** ~1,200–2,000 valid edges (depends on draft constraints).

### Graph Properties
- **Undirected** (edges added in both directions)
- **Weighted** (weights are vessel-dependent and recomputed per request)
- **Cached** in-memory for 5 minutes after first build (TTL-based)
- **No inner-loop DB queries** — graph loaded once, pathfinding runs in pure JS

## 2. Optimization Objective

Two routes are computed per request:

| Route | Algorithm | Objective |
|---|---|---|
| Standard | Dijkstra | Minimize total distance (NM) |
| Optimized | A* | Minimize weighted composite cost |

---

## 3. Cost Function

### Multi-Objective Composite Edge Cost

```
cost(edge) = wFuel   × norm(fuelCost)
           + wTime   × norm(travelTimeHrs)
           + wSafety × norm(safetyRisk)
```

Where `norm(x)` applies **min-max normalization** across all graph edges:
```
norm(x) = (x - min_x) / (max_x - min_x)   ∈ [0, 1]
```

This ensures fuel (tons), time (hours), and risk (0-100) are all on the same scale before weighting.

### Weight Derivation from Boolean Priorities

```
HIGH_SHARE = 0.85  (distributed equally among true priorities)
LOW_SHARE  = 0.15  (distributed equally among false priorities)
```

| priorities.fuel | priorities.time | priorities.safety | wFuel  | wTime  | wSafety |
|---|---|---|---|---|---|
| true  | false | true  | 0.425 | 0.150 | 0.425 |
| true  | true  | false | 0.425 | 0.425 | 0.150 |
| false | true  | true  | 0.075 | 0.425 | 0.425 |  ← corrected
| true  | false | false | 0.850 | 0.075 | 0.075 |
| false | false | true  | 0.075 | 0.075 | 0.850 |
| true  | true  | true  | 0.333 | 0.333 | 0.333 |
| false | false | false | 0.333 | 0.333 | 0.333 |

Weights always sum to exactly 1.0.

### Weather Risk Injection

When Member 3 provides weather conditions:
```
effectiveRisk(edge) = baseRisk + weatherBoost

weatherBoost = max over all weather observations w within 200 NM of edge midpoint of:
               w.riskScore × (1 - distance(midpoint, w) / 200) × 0.5
```

Max additional risk contribution: 50 points. Falls back to base risk if weather unavailable.

## 4. Algorithm

### Standard Route: Dijkstra

```
Objective: minimize sum of distanceNM over path
Complexity: O((V + E) log V) with binary min-heap
V ≈ 85, E ≈ 1500 → runs in < 1ms
```

### Optimized Route: A*

```
Objective: minimize sum of composite cost(edge) over path
Heuristic: h(n) = haversineNM(n, destination) / maxSpeed × wTime
```

**Admissibility proof:**
- `haversineNM(n, dest)` is the minimum possible remaining distance (great-circle lower bound)
- Dividing by `maxSpeed` gives the minimum possible remaining time
- Multiplying by `wTime` gives the minimum possible remaining cost contribution from time
- The heuristic never includes fuel or safety components (those are ≥ 0 for the remaining path)
- Therefore `h(n) ≤ actual remaining cost` — the heuristic is admissible
- The heuristic is also monotone (consistent), so A* is guaranteed to find the globally optimal path

**Complexity:** O((V + E) log V) worst case; typically much better with heuristic pruning.

**Determinism:** No `Math.random()`. Tie-breaking by node ID string comparison ensures identical inputs always produce identical outputs.

## 5. Vessel Constraints

| Constraint | Effect |
|---|---|
| `draft` | Edges where `vessel.draft > edge.maxDraft` are excluded from the graph |
| `maxSpeed` | Used in `travelTimeHrs = distanceNM / maxSpeed` and A* heuristic |
| `fuelConsumption` | Used in `fuelCost = distanceNM × fuelConsumption` |
| `type` | Stored in request record; future routing rules can filter by vessel type |

## 8. Complexity Summary

| Operation | Complexity |
|---|---|
| Graph build (first call) | O(N²) where N = ~85 nodes → ~7,225 pairs evaluated |
| Dijkstra | O((V+E) log V) ≈ O(1500 × 6.4) ≈ ~10,000 ops |
| A* | O((V+E) log V) typically 2-5× faster than Dijkstra due to heuristic |
| Normalization bounds | O(E) one pass |
| Weather injection | O(W × E) where W = weather points; bounded by proximity filter |
| **Total per request** | **< 10ms** for this graph size |

---

## 9. Limitations

1. **Land crossing**: The graph does not implement a polygon-based land avoidance system. The waypoints guide the graph topology around landmasses, but unusual port pairs may occasionally produce geometrically suboptimal paths.
2. **Shallow water detail**: `maxDraft` per edge is approximate (based on known strait/channel depths), not derived from a bathymetric database.
3. **Real-time AIS**: The engine uses static port coordinates, not live ship positions.
4. **Weather**: Integration with Member 3's weather API is complete at the interface level; actual weather data quality depends on Member 3's implementation.
5. **Tidal effects**: Not modelled.
6. **Piracy zones**: Encoded as elevated `baseRisk` on specific waypoints; not a formal maritime security dataset.
